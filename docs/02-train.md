# 02 · 训练

模型是在**游戏外**用 numpy 训出来的，训完把 `Wq Wk Wv Wo W1 W2 g b Wout` 九个数组存成 npz，再交给生成器编成 mlog。这一篇讲语料怎么来、怎么洗、超参是什么、指标怎么读，以及你想用自己的语料重训时要对齐哪些东西。

---

## 0. 一览

| 项 | 值 |
| --- | --- |
| 训练脚本 | `train/train.py`（numpy 手写反向 + Adam） |
| 语料构建 | `train/build_corpus.py`（清洗 + 词表） |
| 语料规模 | 24.6 万字中文（字符级清洗后） |
| train / val token | 224,714 / 21,646 |
| 词表 | 4096，字符级 |
| 步数 | 12,000 |
| batch | 128 |
| 学习率 | 2e-3（Adam） |
| 优化器 | 手写 Adam，无框架依赖 |
| val_ppl | 94.8 |
| top-1 | 18.5% |

训练的产物就是仓库里的 `weights/mlogpt-zh-0.72m-fp32.npz`（5,771,362 B）。**正常情况下你不需要重训**——权重已经在了，只有想换语料或换规模时才需要往下看。

---

## 1. 语料：24.6 万字从哪来

语料是从作者本机的一批中文文档里抽的，**没有随仓库分发**（来源是私人文档，也不适合打包）。所以「完全复现这一次训练」做不到；能复现的是**流程**和**结构**，不是这一份权重。

清洗规则（`train/build_corpus.py`）：

1. 去掉代码块（``` 围起来的部分）；
2. 去掉表格（`|` 分隔的行）；
3. 去掉 frontmatter（文件头 `---` 包裹的元数据）；
4. 只保留 CJK 字符与中文标点，其余（英文、数字、URL、控制符）全部丢弃；
5. 连续空白折叠，按固定比例切 train / val。

结果：

```
24.6 万字  →  224,714 train tokens  +  21,646 val tokens  =  246,360 tokens
```

字符级分词下 1 个字 = 1 个 token，所以 246,360 和「24.6 万字」是对得上的——这也是一处可以自查的地方：如果你的清洗结果和这个数量级差很远，说明规则跑偏了（比如把英文全留下了，或者把标点也删了）。

为什么要把英文/数字全删掉？因为词表只有 4096 个位置，全给汉字和中文标点。混进英文会让大量字符落到「未命中 → id 0」上，等于往语料里灌噪声。

---

## 2. 词表与分词：4096 个字符

- 字符级：一个汉字一个 token，一个中文标点也一个 token；
- 词表大小 4096，取语料里出现频次最高的 4096 个字符；
- **未命中记 id 0**（不是报错、不是跳过）；
- 词表以 JSON 形式给出（`weights/vocab-zh-4096.json`），id → 字符的映射必须与训练时完全一致。

为什么坚持字符级？因为推理侧的分词是**在 mlog 里做的**：144 台处理器逐字符比较，把你的输入查成 token id（细节在 [03](03-inference-in-mlog.md)）。词表越大，比较次数越多；字符级 + 4096 是能在这个预算里做完的规模。如果用 BPE，分词本身就得在游戏里跑一个子词合并算法，不现实。

字符级的代价：序列变长。一句 10 个字的话就是 10 个 token，而窗口只有 16——这就是为什么它只能看最近十几个字（见 [05](05-limits.md)）。

---

## 3. 目标函数与梯度

标准的 next-token 交叉熵，没有花活：

```
loss = -mean( log softmax(h_L @ Wout)[target] )
```

反向传播是**手写**的：`train/train.py` 里没有 autograd，每个矩阵的梯度都按公式写出来，包括 LayerNorm 的反向。这样做不是因为喜欢手写，而是因为整个项目要求「只用 stdlib + numpy」。

有一个地方特别容易写错，值得单独说：**4 层共享同一组权重**（见 [01 §3](01-model.md)）。这意味着反向传播时，同一个 `Wq` 会在 4 个不同的递归步上各产生一份梯度，必须**累加**后再更新。如果按「4 个独立层」的直觉去写，要么漏掉 3 份梯度，要么把 4 份当成 4 个不同的参数——前者训不动，后者参数形状直接对不上。

```
dWq = 0
for li in 1..L:
    dWq += 该步的 dWq      # 共享权重 → 梯度累加
Wq -= Adam(dWq)
```

另一处：因为只有最后一个位置跨层流动（[01 §4](01-model.md)），反向也只需要沿 `h` 这一条链回传，`X` 侧不回传（嵌入是解析式的，本来就没有参数）。这让手写反向的工作量小了很多——如果按标准 Transformer 写，`S × d` 的隐藏状态每一层都要回传。

## 4. 超参

| 超参 | 值 | 备注 |
| --- | --- | --- |
| 步数 | 12,000 | 固定步数，不是 early stop |
| batch | 128 | |
| 学习率 | 2e-3 | Adam 默认其余系数 |
| 优化器 | 手写 Adam | 无权重衰减记录 |
| 精度 | float32 | 与 npz 一致 |

算一下看过多少数据（推算）：`12,000 × 128 = 1,536,000` 个 token 位置，除以 224,714 个训练 token，约 **6.8 个 epoch**。对一个 0.72M 参数、24.6 万字语料的模型来说，这个量级已经进入「该担心过拟合而不是欠拟合」的区间——所以「再多训几万步」通常不是提升质量的正路。

学习率调度（warmup / 衰减）没有单独记录；复现时从常数 `2e-3` 开始是可以跑通的起点，但不要把它当成「作者当时一定这么干」的确证。

## 5. 指标怎么读

```
val_ppl  = 94.8      （均匀分布在 4096 类上是 4096）
top-1    = 18.5%     （随机猜是 1/4096 ≈ 0.024%）
```

**ppl 94.8 是什么意思。** perplexity 是「平均每一步要在多少个等概率候选里分摊」。94.8 意味着模型把 4096 个候选压缩成了大约 95 个「有效候选」。折算成每字符的负对数似然是 `ln(94.8) ≈ 4.55` nat（推算）。比均匀分布（4096，即 8.32 nat）好了将近一半的比特数——它**确实学到了中文的局部搭配**，不是随机数发生器。

**为什么这仍然不算「能用」。** top-1 只有 18.5%：五分之四的时候，它押的那个字不是正确的下一个字。ppl 只看分布是否集中，top-1 看分布是否压在**对的那个**字上。一个能顺着你意思写下去的中文模型，这两项会同时好一大截；这里只有前者勉强及格。

真实输出的样子（全尺寸，headless 实测）：

```
输入：量持法
输出：同任意只相同（所
```

读起来像「术语碎片」，不是句子。这不是采样参数没调好——temperature 就是 1.0，换温度只会让碎片更碎或更重复。

### 指标为什么上不去（判断，非消融结论）

仓库里**没有做过消融实验**，下面是从结构出发的判断，不是实测排序：

1. **嵌入不可学习**（解析式正弦，见 01 §2）。词的表示是固定的伪随机向量，模型只能在其上做线性组合，这大概是最大的天花板。
2. **语料 24.6 万字**。这个量级能学到字与字的搭配，学不到句法以上的东西。
3. **窗口 16**。上下文只有十几个 token，很多预测本质上无法从上下文推出来。
4. **共享权重 + 单头 + 只有最后位置流动**。容量和交互深度都被压缩过。

## 6. 用自己的语料重训

想要一个「说你的领域黑话」的版本，可以重训。流程如下，**具体参数以脚本的 `--help` 为准**（这里只保证流程与契约，不保证 flag 拼写）：

### 6.1 准备文本

把纯文本（`.txt` / `.md`）放进一个目录。中文为主；英文、数字会在清洗时被丢掉，放进去也没用。

### 6.2 清洗 + 建词表

```bash
python train/build_corpus.py --help
```

它要产出两样东西：

- 训练用的 token 序列（train / val 两份）；
- 词表 JSON：`id → 字符`，长度 4096。

### 6.3 训练

```bash
python train/train.py --help
```

产物是一个 npz，**必须**满足：

| 要求 | 值 |
| --- | --- |
| 键名 | `Wq Wk Wv Wo W1 W2 g b Wout`（少一个都读不了） |
| 形状 | `128×128 / 128×128 / 128×128 / 128×128 / 512×128 / 128×512 / 128 / 128 / 4096×128` |
| 精度 | float32 |
| 参数量 | 721,152 |

### 6.4 重新构建蓝图

换权重之后必须重新 `--build`（权重是被编进语句常量的，不是运行时读的）：

```bash
python mlogpt/gen.py --build \
  --d 128 --S 16 --L 4 --V 4096 --N 8 --cap 900 --seed-tok 82 \
  --table-free --input \
  --weights <你的.npz> --vocab <你的词表.json> --out my-model.msch
```

### 6.5 五个必须对齐的数

`d=128`、`S=16`、`L=4`、`FF=512`、`V=4096`。改了任何一个，权重形状、蓝图里的块数、分词器的分段数都要跟着改；`V` 变了尤其麻烦——144 台分词器是按 4096 个 id 设计的（16 位置 × 9 段 × 至多 456 个 id）。

### 6.6 常见的坑

- **词表顺序不一致**：最容易犯、最难查。字数一样、字符也一样，但 id 对不上，结果是「能跑、输出是乱码」，不会报任何错。
- **未命中字符**：语料里没出现过的字会落到 id 0。用你的语料重训后，换一段别的文本测试，大量 id 0 会让输出迅速退化成重复。
- **清洗过度**：把标点也删了，模型就学不会断句；把换行保留成 token，又会浪费词表位置。
- **共享权重梯度漏累加**：见 §3，症状是 loss 降得很慢或完全不降。
- **直接改 `V` 但不改分词器**：蓝图能生成，但分词器只覆盖旧 id 段，新 id 永远出不来。

## 7. 常见误解与反例

**误解：ppl 94.8 说明训练失败了。**
反例：均匀分布是 4096，随机猜的 top-1 是 1/4096 ≈ 0.024%。94.8 和 18.5% 都远好于随机——它学到了东西，只是没学到「够用」。判断失败要看它是否低于基线，不是看它是否达到你的期待。

**误解：再多训几万步就能变好。**
反例：12,000 步 × batch 128 已经把 224,714 个训练 token 过了约 6.8 遍（推算）。在 0.72M 参数、随机固定嵌入、单头、窗口 16 的结构下，继续加步数更可能是在拟合这 24.6 万字，而不是学会中文。**没有做过这条消融**，所以这只是判断；但「先加数据、再改结构、最后才加步数」是更安全的顺序。

**误解：训练用了 PyTorch，仓库只是没写依赖。**
反例：`requirements.txt` 里只有 `numpy>=1.24`，反向传播是手写的，包括 LayerNorm。整个项目（训练、构建、参考前向、网页外壳）都只用 stdlib + numpy。这也是为什么仓库能在任何装了 numpy 的机器上直接跑，而不需要配 CUDA。

**误解：既然权重是 float32，重训时用 float64 会更准。**
反例：训练用什么精度不重要，**对齐才重要**。mlog 侧的数值是 double，参考前向按 float32 权重算，蓝图里的常量也是从 float32 权重生成的。你用 float64 训完再存成 float32，没问题；但如果你改了舍入方式（比如量化到 int8），蓝图里的语句和参考实现就对不上了，逐位对拍会立刻失败。
