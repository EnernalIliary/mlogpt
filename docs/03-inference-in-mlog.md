# 03 · 在 mlog 里做推理

这一篇讲编译：一个 numpy 前向怎么变成 8,767,542 条 mlog 语句、为什么被切成 10,786 块、块与块之间怎么同步、输入的字怎么变成 token id。

读完你应该能回答一个具体问题：**为什么 8 个字要 42.7 秒。**

---

## 0. 目标平台：mlog 能给什么

mlog 是 Mindustry 逻辑处理器的脚本语言，本质是一台很窄的栈式/变量式机器：

| 能力 | 有没有 | 说明 |
| --- | --- | --- |
| 标量变量 | 有 | 双精度数、对象引用 |
| 内存 | 只有 memory cell | 一个 cell 存一个数，读写各一条语句 |
| 数组 / 指针 / 结构体 | **没有** | 一切都要展开成直线代码 |
| 循环 | 只有 jump | 会吃掉每 tick 的语句预算 |
| 跨处理器通信 | 只有 memory cell | 没有消息队列、没有共享内存 |
| 单台语句上限 | **999 条** | 硬上限 |
| 单台执行速率 | `setrate 1000` ⇒ 1000 条/tick | 全阵列都用这个设置 |
| 浮点 | 双精度 | 没有 int 类型，整数靠约定 |

这五条（没有数组、没有共享内存、999 条、1000 条/tick、只有 cell 通信）决定了后面所有的设计。

---

## 1. 数值表示

**权重不是运行时读的。** mlog 没有文件 I/O，所以 721,152 个参数必须在**生成蓝图时**就变成语句里的字面常量。这就是 71.41 MB 产物的主要来源：不是模型大，是指令流大。

```
numpy:  y = x @ W          # W 是 512×128 的数组
mlog:   op mul   t0  x0  w00        # w00 = W[0][0]，构建时折成字面量
        op madd  t1  x1  w10  t0   # 示意：乘加，w10 = W[1][0]
        ...                          # 65,536 次
```

要点：

- **精度**：权重是 float32 存盘，写进语句时按十进制字面量展开；mlog 内部按双精度算。参考实现（`reference.py`）用 float32 权重做同样的运算，两边能逐位对上，说明这条链路没有引入可见的舍入分歧。
- **中间量**：全部是双精度标量。没有定点、没有量化——量化会立刻破坏与参考实现的逐位一致性，也就没法证明「算对了」。
- **token id**：也是双精度数，只是约定按整数用（0..4095）。未命中的字符记 0。

---

## 2. 一次矩阵乘怎么变成语句

没有数组，`y = x @ W` 只能逐元素展开。一个 128 → 512 的投影，写法是：

```
# y[i] = Σ_j x[j] * W[j][i]
for i in 0..511:
    acc = 0
    for j in 0..127:
        acc = acc + x[j] * W[j][i]
    y[i] = acc
```

每条内层语句在 mlog 里对应「取一个常量（权重）、一次乘、一次加」。理论上可以把 `W[j][i]` 折成字面量，于是每条内层循环变成 1~2 条语句。`128 × 512` 的一次投影就是 65,536 次乘加——这就是为什么单台处理器装不下任何一层。

实际计数（实测，不是估算；每行都是把 `.msch` 里同一类处理器逐块数出来的，块数相加等于 10,786）：

| 项 | 块数 | 语句数 |
| --- | --- | --- |
| 前向（4 层共享 block + 注意力 + FFN） | 9,108 | 7,362,930 |
| 输出头（4096 行 logits） | 1,366 | 1,254,836 |
| 采样与回写（8 个位置） | 72 | 66,400 |
| 分词器（16 位置 × 9 id 段） | 144 | 56,640 |
| 嵌入预载 | 16 | 8,352 |
| 归约 / 扫描 / 裁前缀 | 77 | 7,462 |
| driver / init / reporter（含说明、状态面板） | 3 | 183 |
| 轮询节流 `wait 0`（v0.1.1） | —（加在各轮询块里） | 10,739 |
| **合计** | **10,786** | **8,767,542** |

前向占 84.0%（7,362,930 / 8,767,542），其余 1,404,612 条落在上面那些非前向块里。加上游戏内的说明面板 / 状态面板后，`reporter` 块连同 `init`、`driver` 的面板写入一共 183 条；新增的说明 / 状态面板让总数比没有面板的那一版正好多 47 条，且 47 条全部落在非前向块里。v0.1.1 的轮询节流（每个依赖轮询循环加一条 `wait 0`）又加了 10,739 条，也全在非前向块里。

## 3. 切块：999 条的天花板

一条直线程序有 7,362,930 条语句，而单台处理器最多 999 条，所以必须切开：

```
7,362,930 / 999 ≈ 7,370   ← 理论最少块数（全部塞满）
实际：9,108 块（前向部分；因为要留同步余量、且每块要带读写和同步语句）
整个阵列 10,786 台 = 前向 9,108 + 输出头 1,366 + 分词器 144 + 采样/预载/驱动等 168
```

切块由 `mlogpt/rig.py` / `mlogpt/rig_chain.py`（vendored 自 [mlog-agentskill](https://github.com/EnernalIliary/mlog-agentskill)）完成，规则大致是：

1. 把线性化的语句序列按 `--cap 900` 切成目标块；
2. 找出跨块的变量依赖（A 块算出的值被 B 块用）；
3. 在块头加「从 cell 读」，在块尾加「写 cell」，中间补同步语句。

注意 `--cap 900` 是**目标**，不是结果：重写阶段插入的读写与同步会把实际行数推高。实测单台最多 **984 行**，离 999 还有 15 行余量——切块已经贴着硬上限在走，几乎没有余量再塞东西。

填满程度（推算）：`8,767,542 / (10,786 × 999) ≈ 81.4%`。想再加宽一层，这条线会立刻撞穿。

## 4. 跨块传值：memory cell + barrier

块与块之间只能靠 memory cell 传数。整个阵列用了 **170 个** memory cell。

一个数从 A 块到 B 块要走三步：

```
A:  write  value  cell_k  0        # 把结果落格
A:  登记「我到了」                  # 同步点
B:  read   value  cell_k  0        # 取值
```

关键在于第二步：B 必须保证 A **已经写完**，否则读到的是上一轮的旧值。这就是 barrier。

> 下面这段是**语义示意**，不是生成器逐条产出的代码；真正的实现（计数怎么记、自旋怎么退）在 vendored 的 `rig_chain.py` 里。

```
# 块尾：报告自己完成
op add  n  n  1
write   n  __barrier  0

# 块首：等到所有参与者都完成
loop:
  read  v  __barrier  0
  jump  loop  lessThan  v  <本波次块数>
```

barrier 的代价不是「一条语句」，而是**最慢的那台决定所有人**。一个波次里只要有一台多跑了几百条，整个阵列一起等。这就是为什么后面所有性能讨论都绕不开它。

## 5. 一个 token 的时序

把 10,786 块按依赖排成波次（wave），每个波次内的块可以并行：

```
wave 1  嵌入 + 第 1 层的 LN/q 投影
wave 2  K/V + 注意力打分 + softmax 累加
wave 3  注意力加权 + Wo 残差
wave 4  第 1 层的 FFN（128→512→128）
wave 5  第 2~4 层（同构，波次复用）
wave 6  输出头 128 → 4096
wave 7  采样（一次比较）
wave 8  写 message 方块
```

（上面的波次划分是结构上的必然顺序，具体哪几条语句落在哪个波次由生成器决定。）

实测给出两个可以直接对照的数字：

| 量 | 值 |
| --- | --- |
| 8 个 token 的总 tick | 60 |
| 每 token 的 tick | 60 / 8 = 7.5（推算） |
| 每 token 的同步点 | 7~8 |

**7.5 ≈ 7~8**，这不是巧合：一个 token 的墙钟时间基本等于「同步点的个数」，也就是每 tick 大致只前进一个同步点。真正花在算数上的时间被压在同步的缝里。

换算成墙钟：42.7 s / 60 tick ≈ 0.71 s/tick（推算）。这个数在 [04](04-performance.md) 里会被拆开看。

## 6. 输入：144 台分词器

游戏里没有「字符串 API」可用，所以分词是在 mlog 里硬做的：

```
16 个位置  ×  9 个 id 段  =  144 台分词器
每段最多 456 个 id  →  9 × 456 = 4,104 ≥ 4,096  ✓
```

每台分词器负责「第 p 个字符是否等于词表里第 s 段中的某个字」：它把自己那 456 个候选字与输入字符逐个比较，命中就把对应的 id 写进 cell；全不命中就留 0（与训练时的「未命中记 id 0」一致）。

为什么是 16 个位置？因为窗口 S = 16。为什么是 9 段？因为 4096 / 456 向上取整是 9。这两个数都是被模型规格倒推出来的，不是随便挑的。

整个分词阶段只有输入的那一轮跑一次，不是每个 token 都跑。

---

## 7. 触发与多轮

驱动逻辑（`--input` / `driver`）是这样的：

```
1. 检测 message11（输入块）文本非空
2. 等 0.3 s，让 144 台分词器把 16 个位置都填好
3. 跑 N = 8 个 token 的前向 + 采样
4. 把 8 个字写到 message1..8
5. 等 message11 被清空 —— 清空后才接下一轮
```

**第 2 步的 0.3 s 是必须的。** 144 台分词器是并行跑的，driver 没有任何办法知道它们什么时候全部写完（没有「就绪」信号可用），只能固定等一段时间。等太短会读到上一轮的旧 id，等太长则白等。0.3 s 是一个实测能稳定工作的值。

**第 5 步决定了它是「多轮」的**：只要你不清空输入块，它就不会重算——否则同一个输入会被反复生成，看起来像卡死。想再问一句，先清空，再打字。

---

## 8. 输出：8 个 message 方块

```
message1  message2  message3  message4
message5  message6  message7  message8
```

每 4 个 token 换一行，所以是 2 行 × 4 字。8 个 token 正好铺满——`N = 8` 这个数就是被方块布局定死的，不是模型能力决定的。

实测时 message 上显示的是「同任意只相同（所」，加上输入块本身的原样回显。

## 10. 常见误解与反例

**误解：把 71 MB 的蓝图导进游戏就等于装好了模型，能像聊天框一样用。**
反例：导入只是第一步。你得在 `message11` 里打字、等 42.7 s、清空、再打字。它不是「输入框 + 回车」，是一个需要手动清空才能重启的批处理循环。而且它只输出 8 个字。

**误解：处理器越多越快，加到两万台就能快一倍。**
反例：现在 10,786 台已经把语句预算填到约 81.4%（推算）；真正卡时间的是每 token 7~8 个同步点。加到两万台只会在每个波次里多塞一批「一起等」的处理器，墙钟时间不会按比例下降。**先减同步点，再谈加机器。**

**误解：分词器 144 台，说明分词很贵。**
反例：分词只在输入那一轮跑一次（8 个 token 的前向要跑 8 次）。它不值钱。真正贵的是每一步前向都要跨块同步。

**误解：既然是对拍，那一定是逐位精确的浮点等价。**
反例：这里的一致是**token id 序列一致**，不是在比 logits 的最后一位。mlog 用双精度、参考实现用 float32 权重，两侧的十进制字面量也可能有末位差异；只要 argmax/采样落点相同，id 序列就相同。这不等于「数值完全等价」，也不该被这么宣传。

**误解：0.3 s 是随便写的魔法数，改成 0.1 s 也能跑。**
反例：0.3 s 是给 144 台分词器的稳定窗口。缩短它，某些位置可能还没写完就被读走，症状是「偶尔有一个字错」——这种错在一次性对拍里很容易被漏掉。

## 11. 自己跑一遍

```bash
# 1) 构建（约 52 s，产出 71.41 MB）
python mlogpt/gen.py --build \
  --d 128 --S 16 --L 4 --V 4096 --N 8 --cap 900 --seed-tok 82 \
  --table-free --input --input-text 量持法 \
  --weights weights/mlogpt-zh-0.72m-fp32.npz \
  --vocab  weights/vocab-zh-4096.json --out mlogpt-zh-0.72m.msch

# 2) 走真实执行器（需要 v160.7 server jar + JRE21 + 姊妹仓的 tools/mlogsim.py）
python mlogpt/gen.py --run mlogpt-zh-0.72m.msch --ticks 120 --input-text 量持法
```

`--run` 的 `--ticks 120` 给的是余量：实测 8 个字 60 tick，留一倍冗余便于观察末尾的输出写入。
