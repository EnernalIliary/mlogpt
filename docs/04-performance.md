# 04 · 性能

这一篇只做一件事：把 42.7 秒拆开，看它花在哪，以及哪些「优化」其实没用。

先给结论：**它不是算力不够，是同步太多。** 8 个字要走 60 个 tick，而每个 token 的关键路径上有 7~8 个同步点——时间基本等于同步点的个数乘以每次同步的代价，跟阵列里塞了多少台处理器关系不大。

---

## 0. 实测表

全部来自一次完整构建 + 一次 headless 实跑：

| 量 | 实测值 |
| --- | --- |
| 处理器 | 10,786 台（全部 world processor） |
| 单台速率设置 | `setrate 1000`（1000 条/tick/台） |
| memory cell | 170 个 |
| message 方块 | 11 个（输出 1~8 ｜ 说明 ｜ 状态 ｜ 输入，最右） |
| 方块总数（tiles） | 10,966 |
| 语句总数 | 8,756,803 |
| 前向语句 | 7,362,930（84.1%） |
| 单台最多语句 | 983 行（硬上限 999） |
| 蓝图大小 | 71.32 MB |
| 构建耗时 | 约 63 s |
| 8 个 token 的 tick 数 | 60 |
| 8 个 token 的墙钟 | 42.7 s |
| 每 token 墙钟 | 约 5 s |
| 每 token 同步点 | 7~8 |
| 理论算力上限 | 比实测快约 10 倍 |

从这张表能直接推几个数（下面都标了「推算」，它们不是独立观测）：

| 推算 | 算式 | 值 |
| --- | --- | --- |
| 每 token tick | 60 / 8 | 7.5 |
| 每 tick 墙钟 | 42.7 / 60 | ≈ 0.71 s |
| 语句预算填充率 | 8,756,803 / (10,786 × 999) | ≈ 81.3% |
| 端到端语句吞吐 | 8 × 7,362,930 / 42.7 | ≈ 138 万条/秒 |
| 输出头参数占比 | 524,288 / 721,152 | 72.7% |

「端到端语句吞吐」这个数要小心读：它把处理器在 barrier 上空等的时间也算进了分母，所以是个**下界**，不代表执行器的峰值能力。

## 1. 时间花在哪：三层拆解

一颗 token 的墙钟可以写成：

```
T_token  ≈  Σ(每个波次的执行时间)  +  Σ(每次 barrier 的等待)
         =  波次数 × (每波次执行 + 同步开销)
```

现在有三个已知量可以把这条式子校准：`T_token ≈ 5.3 s`、`tick/token = 7.5`、`同步点/token = 7~8`。三者一致得有点刺眼：**每 tick 差不多正好过一个同步点。**

这意味着：

1. 一个波次的工作量（若块按波次划分，平均每台约 812 条语句）能在**一个 tick** 内跑完——1000 条/tick 的预算刚好够；
2. 剩下的时间不是在算，而是在等：等最慢的那台到齐、等 barrier 放行、等下一个 tick 开始；
3. 所以「加处理器」不会让 `tick/token` 下降，它只会在每个波次里多塞一批一起等的机器。

### 每个 tick 只用掉约一成的语句预算

还有一组数更能说明问题。每 tick 的语句预算是：

```
10,786 台 × 1000 条/tick = 10,786,000 条/tick
一个 token 的前向 7,362,930 条，摊到 7.5 个 tick ≈ 981,724 条/tick
→ 预算用量 ≈ 9%（推算）
```

也就是说：**每个 tick 里，阵列有大约九成的执行槽位是空的。** 这不是「语句太少」，而是「大部分处理器在等」。

### 波次是串行的，阵列大部分时间是闲的

7~8 个同步点意味着一次前向被切成 7~8 个**串行**的波次。如果块是按波次划分的（依赖链上相邻的块不能同时跑），那么任一时刻只有约 `10,786 / 7.5 ≈ 1,438` 台在干活（推算），其余在等——阵列利用率约 13%。这个数恰好和「理论上限快约 10 倍」是同一个量级（1 / 0.13 ≈ 7.7）。

也可能块不是按波次切的，而是每台都参与每个波次（那样瓶颈就纯粹是 barrier 的固定开销）。两种读法的细节不同，但**结论一样**：墙钟由同步点的数量决定，不由语句总量决定。要判断实际是哪一种，看两件事就够了——每个波次里有多少台处理器写了 cell、以及每次 barrier 的等待占多少 tick。仓库目前没有导出这两项数据（属于**未验证**）。

## 2. 「理论算力上限快 10 倍」怎么理解

这句话不是「换台好电脑能快 10 倍」，而是：

```
如果 barrier 不花时间、每个波次结束时所有处理器都恰好同时到齐，
同样的语句量（8,756,803 条）能在约 42.7 / 10 ≈ 4.3 s 内跑完。
```

也就是说 42.7 s 里有大约 **90% 是同步与空等**，不是乘加。这个判断的用处在于：它把优化方向从「怎么算得更快」扭到了「怎么少同步几次」。

注意这是**上界估计**，不是实测：要证实它，得把 barrier 换成「不等待」的版本跑一次（结果会错，但时间有意义）。这一步仓库里没做，所以「10 倍」是作者根据结构与两个实测量给出的判断，标为**未验证**。

## 3. 构建时间：63 s 与 71.32 MB

构建是一次性成本，但值得知道它由什么决定：

| 项 | 量级 | 说明 |
| --- | --- | --- |
| 语句生成 | 8,756,803 条 | 纯 Python 循环，逐条拼字符串 |
| 产物 | 71.32 MB | 语句文本 + 蓝图容器 |
| 耗时 | 约 63 s | 单线程 |

换算一下（推算）：约 13.9 万条语句/秒、约 1.13 MB/s。这个速度对一次性构建够用，对「改一点参数就想看结果」的迭代显然太慢——所以玩具配置（几十条语句量级）才是自检的入口，全尺寸只在最后验一次。

## 4. 提速方向（按性价比排）

| 方向 | 预期收益 | 是否改变数值 | 把握 |
| --- | --- | --- | --- |
| 4.1 减少同步点 | 大（按比例） | 否 | 高 |
| 4.2 K/V 跨层复用 | 中 | 否 | 未验证 |
| 4.3 提高波次内并行 | 小~中 | 否 | 中（有 trade-off） |
| 4.4 缩小输出头 | 中 | **是** | 会破坏对拍 |
| 4.5 减语句总数 | 很小 | 否 | 低（不降同步） |
| 4.6 提高 setrate | 0 | 否 | 已到上限 |

### 4.1 减少同步点（最有价值）

墙钟 ≈ 同步点数 × 每次同步代价。把 7~8 降到 5，理论上就是 30% 的下降，而且**不改变任何数值结果**。可做的：

- 把同一波次里「写 cell → barrier → 读 cell」的成对操作合并（能在一个处理器内部完成的，就别跨块）；
- 让输出头（128 → 4096）和采样共用一个波次，而不是先落格再取；
- 检查每层内部是否有多余的同步（FFN 的 128→512 和 512→128 之间不该有同步点，它们在同一块里）。

这一条的风险最低、收益最确定。

### 4.2 利用「K/V 与层无关」做常量折叠

4 层共享 `Wk/Wv`，而 context `X` 在整个前向里不变（见 [01 §3](01-model.md)），所以 `K = X @ Wk`、`V = X @ Wv` 在 4 层里是同一份。数学上**只算一次、跨层复用**是无损的。

当前生成器是否已经折叠、折叠后能省多少语句，**未验证**——这一条是结构上看得到的机会，不是已验证的收益。

### 4.3 提高波次内的并行度

如果 4.1 的判断成立（阵列大部分时间在等），那么把每个波次的语句摊到更多处理器上，会让「波次执行时间」下降——但波次数量不变，所以收益有限，且切得更细会引入更多跨块依赖，反过来增加同步点。这是一个明确的 trade-off，不是免费的。

### 4.4 缩小输出头

`Wout` 是 4096 × 128，占全部参数的 **72.7%**（推算），也是单块最大的工作量。任何无损的降低它代价的办法收益都很直接。但要小心：低秩分解、只算 top-k 之类**会改变数值结果**，逐位对拍会立刻失败。要做就只能接受「对不上了」。

### 4.5 减少语句总数（而不是减少同步）

比如常量折叠、把重复的乘加合并、用更小的 `d`/`FF`。这条路的问题是：语句数下降不等于墙钟下降——只要同步点数不变，墙钟基本不动（见 §1）。所以它应该排在 4.1 之后，而不是之前。

### 4.6 提高 `setrate`

已经是 1000，这是设置上限。而且就算能更高，每 tick 过一个同步点的结构也不会自己变快。

## 5. 不要做的事

**不要靠加处理器提速。** 现在 10,786 台已经把语句预算填到约 81.3%（推算）。加机器只会让每个波次里多一批一起等的处理器；`tick/token` 还是 7.5。

**不要把 `--cap` 顶到 999。** 实测单台最多 983 行，离上限只有 16 行余量。为省不到 2% 的块数去冒「某台超限、蓝图导入失败」的风险，不划算。

**不要量化成 fp16 / int8。** 精度一变，与 `reference.py` 的 token 对拍就没了。这个项目全部的说服力都建立在「逐位一致」上，省下来的那点语句数换不回它。

**不要指望多开 message 块并行生成**。自回归生成下，第 k+1 个字依赖第 k 个字，没法并行；多开只会让语句数翻倍。

## 6. 常见误解与反例

**误解：42.7 s 是因为 headless 执行器用 Python 写的，太慢。**
反例：执行器确实不快，但同一个执行器跑玩具配置是几秒级的东西（语句量差三个数量级）。真正把时间拉开的是「每 token 7~8 次同步 × 8 个 token」。如果瓶颈在执行器的解释速度，减少语句数应该线性变快；而按 §1 的分析，减少同步点才会。这两条预言可以用一次实验区分——目前没做，属于**未验证**。

**误解：42.7 s 里有很多时间是游戏在渲染画面。**
反例：这组数字来自 headless 执行，没有画面、没有渲染、没有玩家。它测的就是纯逻辑执行。在有画面的游戏里只会更慢，不会更快。

**误解：71.32 MB 的蓝图加载慢，所以运行慢。**
反例：加载是一次性的（和 63 s 构建一样）。运行时的 42.7 s 与蓝图大小无关，只与语句数、同步点数有关。

**误解：多给点 memory cell 就能缓存中间结果、变快。**
反例：现在用了 170 个 cell，瓶颈不在「存不下」而在「等不齐」。多给 cell 不会减少同步点；反而可能诱导你把本该在一个块里算完的东西拆到两块去。

**误解：「理论快 10 倍」意味着优化完就能到 4.3 s，可以交互了。**
反例：4.3 s 出 8 个字，也还是 0.5 s/字，离「打字即答」差得远。而且 10 倍是上界估计（§2），不是承诺。这个项目的目标不是做一个快的中文模型，是证明它能跑。

## 7. 复现这组数字

```bash
# 构建：看时间与产物大小
time python mlogpt/gen.py --build \
  --d 128 --S 16 --L 4 --V 4096 --N 8 --cap 900 --seed-tok 82 \
  --table-free --input --input-text 量持法 \
  --weights weights/mlogpt-zh-0.72m-fp32.npz \
  --vocab  weights/vocab-zh-4096.json --out mlogpt-zh-0.72m.msch

# 实跑：看 tick 数与墙钟（需要 jar + JRE21 + 姊妹仓的执行器）
time python mlogpt/gen.py --run mlogpt-zh-0.72m.msch --ticks 120 --input-text 量持法
```

两次跑出来的数会有波动（机器、JVM 预热、后台负载），量级应该稳定在「63 s 构建 / 60 tick / 40 余秒」附近。如果你测到的是 4 s 或 400 s，那是环境问题，不是模型问题。
