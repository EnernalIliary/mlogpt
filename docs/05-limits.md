# 05 · 硬限制

这一篇是防误解清单。如果你只读一节，读这一节。

`mlogpt` 是一个**机制演示**：它证明一个 Transformer 的前向可以被编译成 mlog 并在游戏里跑出正确结果。它不是一个可用的语言模型。下面五条限制里，前两条是模型本身的天花板，后三条是平台和验证给它画的线。**没有一条是「再优化一下就好了」的那种。**

---

## 0. 五条限制一览

| # | 限制 | 关键证据 | 后果 | 能不能绕 |
| --- | --- | --- | --- | --- |
| 1 | 能力：不是能聊天的模型 | val_ppl 94.8、top-1 18.5%，输出是术语碎片 | 只能做「局部搭配」级别的续写 | 不能（要换结构 + 换数据量级） |
| 2 | 上下文与长度：窗口 16、一次 8 个字 | S = 16、N = 8，无状态 | 看不到更早的话，也说不完整一句 | 不能（受 999 条/台约束） |
| 3 | 平台规模：999 条/台、170 个 cell | 10,786 台、8,767,542 条、71.41 MB、预算填充 81.4% | 再宽一层就装不下 | 不能（硬上限） |
| 4 | 速度：约 5 s/字 | 8 个字 60 tick、42.7 s | 不可能交互 | 部分可以（见 04，减同步点） |
| 5 | 验证边界：只验了脚本注入 | 对拍的是注入文本，不是人手打 | 手打路径未验证 | 可以（但没做） |

---

## 1. 限制一：它不是能聊天的模型

### 证据

```
val_ppl = 94.8        （均匀分布在 4096 上是 4096）
top-1   = 18.5%       （随机猜是 0.024%）
```

真实输出（全尺寸实测）：

```
输入：量持法
输出：同任意只相同（所
token: [45,390,400,18,196,45,2,127]
```

这不是采样参数没调好。temperature 就是 1.0，换温度只会让输出的碎片更碎或更重复——因为分布本身就没集中到「正确的下一个字」上。

### 为什么（结构性的原因）

1. **嵌入不可学习**。词向量是固定解析式 `sin(a_i·t + b_i)` 算出来的（[01 §2](01-model.md)），模型只能在随机基底上做线性组合。这是最大的天花板。
2. **语料 24.6 万字**。够学字与字的搭配，不够学句法以上。
3. **窗口 16**。很多下一个字本来就无法从上文推出来。
4. **共享权重 + 单头 + 只有最后位置流动**。交互深度被压过。

### 边界在哪

它能做到：给定几个字，输出「看起来像中文、局部搭配合理」的续写。
它做不到：回答问题、遵循指令、保持主题、写完整句子、记住你上一句说了什么。

**没有「调一调就能对话」的路径。** 要跨过这条线，得换掉嵌入（用可学习的）、换掉窗口（受 999 条限制，见限制三）、换掉数据量级——那已经是另一个项目了。

---

## 2. 限制二：16 个 token 的窗口，8 个字的输出

### 数字

| 项 | 值 | 含义 |
| --- | --- | --- |
| 窗口 S | 16 | 前向最多看 16 个 token |
| 有效上下文 | 15 | 第 16 个位置是「要预测的那个」 |
| 一次生成 N | 8 | 出 8 个字就停 |
| 输出布局 | message1..8 | 每 4 个换行，2 行 × 4 字 |

### 后果

- **早期输入会被挤出去。** 生成是自回归的，新的字滑进窗口尾部，最老的 token 掉出去。写 16 个字之后，你开头打的那几个字它已经看不见了。
- **8 个字是一句话的下限，不是上限。** 它说不了完整的一句话，只能给一个片段。
- **没有状态。** 每轮都是全新的：清空输入块 → 下一轮从头开始。它不记得上一轮生成过什么。
- **多轮要手动清空。** 不清空 `message11`，它不会重算（这是有意的，见 [03 §7](03-inference-in-mlog.md)）。

### 为什么不能加长

窗口每加长 1 个 token，注意力相关的语句就按比例增长；而单台上限 999 条、整个阵列已经填到约 81.4%（推算）。S 从 16 到 32 意味着注意力部分翻倍——这在当前切块策略下没有余量。

## 3. 限制三：平台的硬额度

| 额度 | 值 | 现状 | 余量 |
| --- | --- | --- | --- |
| 单台语句上限 | 999 | 实测最多 984 | 15 行 |
| 单台执行速率 | 1000 条/tick | 已用 `setrate 1000` | 0 |
| memory cell | 170 个 | 已分配 | 取决于切块 |
| 阵列规模 | 10,786 台 | 已铺满 | 语句预算 81.4%（推算） |
| 蓝图体积 | 71.41 MB | 一次构建 | 已是实际产物 |
| 构建耗时 | 约 52 s | 单线程 | 一次性成本 |

### 后果

- **不能「再宽一点」。** d 从 128 到 256，矩阵乘语句按 d² 涨 4 倍，块数跟着涨 4 倍，10,786 台会变成四万多台。这不是「有点大」，是没法在游戏里落地。
- **不能「再深一点」而不付代价。** 4 层共享一套权重（[01 §3](01-model.md)），所以加深只增加语句、不增加参数——但每加一层就多一段串行计算，墙钟跟着涨。
- **贴上限切块是危险的。** 984/999 只剩 15 行；任何在块头块尾多插两条语句的改动都可能让某台超限，而 mlog 超限的后果是**蓝图导入失败**，不是降级运行。
- **紧自旋会烧光预算。** `setrate 1000` 下，一个「读 → 不等就重试」的轮询循环每 tick 能烧掉 1000 条指令的空转预算，整阵列空转被压到 0.167 s/tick。v0.1.1 给每个轮询循环头加了一条 `wait 0`（`LExecutor.java:1219-1224`：参数 ≤ 0 时不推进 `@counter`），空转降到 0.0275 s/tick。自己写轮询循环时这一条不能省。
- **71.41 MB 的导入不是无痛的。** 粘贴蓝图、等阵列放完，本身就是一个需要耐心的操作。

### 为什么这是硬限制

999 和 1000 是 mlog 的语言/运行时约束，不是这个项目选的参数。任何「在 mlog 里跑更大的模型」的方案都要面对同一条线——这也是为什么这个项目的价值在「证明可行」，而不在「跑得动更大的」。

## 4. 限制四：约 5 秒一个字

### 数字

```
8 个字  =  60 tick  =  42.7 s   （headless 实测）
每字    ≈  7.5 tick  ≈  5.3 s
```

### 后果

- 你打完一句，等 40 多秒，得到 8 个字。
- 这不是「慢一点但能用」，是**不能当输入法用**。它更像一次批处理作业。

### 能不能改善

能，但有限。瓶颈是每 token 7~8 个同步点（[04](04-performance.md)），减少同步点是唯一有把握的方向；就算把同步点减半，也是 2~3 s/字。要到「打字即答」，需要的是数量级的变化，而结构上没有那个空间。

**它不会变成一个交互式的东西。** 这一条最好早点接受。

---

## 5. 限制五：验证只到「脚本注入」为止

这是最容易被忽略、但最影响可信度的一条。

### 已经验证的

| 项 | 方式 | 结果 |
| --- | --- | --- |
| 玩具配置（d8/S8/L2/V32/N4） | 注入「数条」 | `[2,12,9,3]`，与 numpy 一致 |
| 玩具配置（第二轮） | 清空后注入「行数」 | `[1,11,17,9]`，与 numpy 一致 |
| 全尺寸（d128/S16/L4/V4096） | 注入「量持法」 | `[45,390,400,18,196,45,2,127]`，与 numpy 一致 |

### 没有验证的

- **人手在游戏里打字。** 上面全部是脚本往 `message11` 写文本。人手敲字走的是游戏 UI 的输入路径，触发链、0.3 s 稳定窗口、清空操作都没有在真人操作下测过。
- **长时间多轮。** 只跑了 1~2 轮。连续几十轮之后 memory cell 会不会残留脏值、随机数序列会不会跑偏，没测。
- **不同硬件/不同版本。** 只在 v160.7 上验过；其它版本的 `setrate`、processor 上限行为未验。
- **大规模导入的稳定性。** 71.41 MB 的蓝图在不同机器上的导入表现未统计。

### 为什么这条重要

「脚本注入一致」证明的是**模型与编译正确**；「人手打字一致」证明的是**整条交互链正确**。前者是后者的必要条件，不是充分条件。文档里所有「实测」都应该按这个口径读。

## 6. 常见误解与反例

**误解：18.5% 的 top-1 太低了，说明代码有 bug。**
反例：18.5% 是**模型能力**，不是实现错误。实现的正确性由另一件事保证：mlog 跑出的 token id 与 numpy 参考**逐位一致**（全尺寸 `[45,390,400,18,196,45,2,127]`）。算错了会得到一个和参考不同的序列；算对了但模型差，会得到一个和参考相同、但读起来像碎片的序列。这里发生的是后者。

**误解：既然 tiny 和全尺寸都对上了，那随便换个配置也一定对。**
反例：tiny 验证的是切块与同步逻辑，全尺寸验证的是 4096 类输出层 + 16 位置窗口 + 解析式嵌入。换一个没测过的配置（比如 S=32、或改 V），两条验证都不覆盖它，必须重新对拍。

**误解：限制都是「暂时」的，硬件变快就好了。**
反例：999 条/台和 1000 条/tick 是 mlog 的语言约束，跟 CPU 快慢无关。哪怕执行器快 100 倍，`8 个字 60 tick` 这个**结构**也不会变——变的只是每 tick 的墙钟。限制 2、3 是结构性的，限制 4 只是限制 2、3 的表现。

**误解：既然只是演示，那 42.7 s 无所谓。**
反例：无所谓的前提是你不打算用它。如果有人照着 README 导入蓝图、打字、等 40 秒得到「同任意只相同（所」，那他的失望是文档的责任。所以 README 把这三个数（94.8 / 18.5% / 42.7 s）放在最显眼的位置。

**误解：未验证的部分影响不大。**
反例：交互链恰好是「玩家能不能真的用」的那一环。模型算得再对，如果手打时因为 0.3 s 窗口太短而偶发错字，体验就是「它有时候胡说」。这条没验，就应该说没验。

## 7. 那它到底有什么用

如果你的目标是下面这些，它是有用的：

- **想知道「一个 Transformer 能不能塞进 mlog」** —— 能，这里是完整的构造、切块、同步与对拍记录；
- **想学「怎么把浮点计算拆成没有数组的直线代码」** —— [03](03-inference-in-mlog.md) 是完整的映射说明；
- **想在一个极端受限的平台上做推理** —— 这里踩过的坑（999 条、170 个 cell、barrier 依赖链）在别的嵌入式目标上同样成立；
- **想要一个能完整讲清楚的小模型** —— 721,152 个参数、9 张矩阵，每一张都能对上账（[01 §6](01-model.md)）。

如果你的目标是下面这些，它帮不上：

- 一个能对话的中文模型；
- 一个能写代码/写文案的工具；
- 一个在游戏里「智能 NPC」的现成方案（延迟和上下文都不够）。

## 8. 如果非要突破某一条

| 想突破 | 必须付出 |
| --- | --- |
| 更高的 top-1 | 可学习嵌入（要存储）、更多语料（24.6 万字 → 数量级提升）、更宽的窗口（撞 999 条） |
| 更长的上下文 | 注意力语句线性增长；当前预算已用 81.4%（推算），没有余量 |
| 更快的出字 | 减同步点（有把握，但到不了交互级）；或换执行平台（就不是「在游戏里跑」了） |
| 更大的模型 | 更多处理器 + 更大的蓝图；d 涨一倍语句涨 4 倍，很快超出「游戏内可导入」的范围 |
| 验证交互链 | 真人手打一轮并记录 token id，与 numpy 对拍——**这件事谁都可以做，目前还没做** |

最后一条值得单独说：它是这份文档里唯一一条**成本很低、但还空着**的验证。如果你在游戏里手打了一次并拿到和 `[45,390,400,18,196,45,2,127]` 不同的结果，那是一个真 bug，值得开 issue。
